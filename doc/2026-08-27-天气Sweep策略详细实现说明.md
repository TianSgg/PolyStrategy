# 天气 Sweep 策略详细实现说明

## 系统总览

天气 Sweep 策略是一个两阶段自动化交易系统，针对 Polymarket 天气温度预测市场：

1. **信号生成服务**（`signal_weather`，端口 8001）：实时监控订单簿，检测 sweep 事件
2. **策略执行服务**（`strategy_weather_sweep`，端口 8003）：接收信号后自动下单交易

### 1.3 城市与候选市场的排序逻辑

Polymarket 为每个城市/方向/日期创建一个 event，包含多个温度区间 market。例如纽约最高温事件可能有：

```
Event: highest-temperature-in-new-york-city-on-august-27-2026
Markets:
  - "83°F or below"     (YES = 到不了 84, NO = 至少 84)
  - "84-85°F"           (YES = 最高温在 84-85, NO = 不在)
  - "86-87°F"
  - "88-89°F"
  - "90-91°F"
  - "92°F or higher"
```

**highest 方向排序**：按温度升序 → `[83, 84, 86, 88, 90, 92]`

逻辑：如果实际最高温为 90°F，那么市场从低温开始逐个被穿越确认：
- "83°F or below" 的 NO token 先变为高确定性（因为实际温度 > 83）
- 然后 "84-85°F" 的 NO token 也变为高确定性
- 直到 "90-91°F" 的 YES token 变为高确定性

**lowest 方向排序**：按温度降序 → `[92, 90, 88, 86, 84, 83]`

逻辑相反：实际最低温从高温档位开始逐个排除。

### 1.4 双监视器前瞻机制

```
candidates (highest方向, 按温度升序):
  index 0: "83°F or below"    ← 已跳过 (NO token 高确定性)
  index 1: "84-85°F"          ← 已跳过 (NO token 高确定性)
  index 2: "86-87°F"          ← main_monitor (full模式)
  index 3: "88-89°F"          ← next_monitor (sweep_only模式)
  index 4: "90-91°F"
  index 5: "92°F or higher"

┌─────────────────────────────────────────────────────────────┐
│  main_monitor (index=2, "86-87°F", mode=full)               │
│  - 监控 YES + NO 两个 token 的订单簿                         │
│  - 检测 sweep (ask 在 0.99/0.98 被清空)                     │
│  - 检测 high-certainty (tick=0.001 持续 60s)                │
│  - 当 NO token 高确定性确认 → emit "no_longer_possible"     │
│  - 当 YES token 高确定性确认 → emit "market_resolved"       │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  next_monitor (index=3, "88-89°F", mode=sweep_only)         │
│  - 监控 YES + NO 两个 token 的订单簿                         │
│  - 仅检测 sweep                                             │
│  - 不启动高确定性确认计时器                                   │
│  - 提供即时覆盖：main 确认后可立即 promote                    │
└─────────────────────────────────────────────────────────────┘
```

**Promote 流程**：当 main_monitor 的 NO token 进入高确定性（`no_longer_possible`）：

```
_promote_next()
    │
    ├── 1. 注销旧 main_monitor (index 2)
    │
    ├── 2. next_monitor → main_monitor
    │       mode 从 "sweep_only" → "full"
    │       检查是否已处于高确定性状态 (check_high_certainty)
    │
    ├── 3. 创建新 next_monitor (index 4)
    │       订阅 WebSocket，获取初始快照
    │
    └── 4. 广播 "next_candidate" 事件
```

### 1.6 WeatherOrderBookMonitor — 信号检测核心算法

#### 1.6.1 本地订单簿维护 (LocalOrderBook)

```python
bids: dict[float, float]  # price → size
asks: dict[float, float]  # price → size

apply_snapshot(bids, asks)  # 完整替换
apply_change(price, size, side)  # 增量更新 (size=0 → 删除该价位)
```

#### 1.6.2 Sweep 检测算法

```
_evaluate(asset_id, previous_asks, high_probability_asset, previous_tick)
    │
    ├── 前提条件 (全部满足才检测 sweep):
    │   ├── previous_asks 不为空 (有之前的 ask 状态)
    │   ├── asset_id == high_probability_asset (只检测概率较高的一侧)
    │   ├── previous_tick == 0.01 (之前是标准 tick)
    │   └── current_tick == 0.01 (当前仍是标准 tick)
    │
    ├── 遍历阈值: [0.99, 0.98]
    │   │
    │   ├── before_exists = 之前在 <= threshold 的价位有 ask 挂单?
    │   ├── after_exists = 现在在 <= threshold 的价位还有 ask 挂单?
    │   │
    │   └── if before_exists AND NOT after_exists:
    │         ★ SWEEP 检测成功!
    │         emit event_type="sweep"
    │         reason="ask_levels_through_0.99_cleared" 或
    │                "ask_levels_through_0.98_cleared"
    │         break (只报告最高阈值)
    │
    └── 更新 _last[asset_id] 快照
```

**关键概念 — higher_probability_asset**：

```
_higher_probability_asset(previous_books):
    对 YES 和 NO 两个 token 分别计算 mid_price = (best_bid + best_ask) / 2
    返回 mid_price 更高的那个 asset_id
    如果两者相等 → 返回 None (不检测)

意义: sweep 只在"被市场看好"的一侧检测
  - NO token mid > YES token mid → 只在 NO 上检测 sweep
  - YES token mid > NO token mid → 只在 YES 上检测 sweep
```

**为什么这样设计**：

当一个温度档的 NO token 被 sweep（例如 "86-87°F" 的 NO 从 0.60 → ask 被清到 0.99 以上），说明大买家认为实际温度必然超过 87°F。这是一个强信号。

#### 1.6.3 高确定性检测算法

```
_evaluate() → 只在 mode="full" 时执行
    │
    ├── _high(asset_id) 判断条件:
    │   ├── tick_size == 0.001 (已从 0.01 缩小)
    │   └── best_ask is None (完全没有卖单)
    │       OR (best_ask >= 0.999 AND best_bid >= 0.995)
    │
    ├── 如果 _high == True 且尚无确认计时器:
    │   └── 启动 60 秒确认计时器 _confirm(asset_id)
    │
    ├── 如果 _high == False 且有进行中的计时器:
    │   └── 取消计时器 (状态回退，不是真正的高确定性)
    │
    └── _confirm(asset_id) 60 秒后:
        ├── 再次检查 _high(asset_id)
        ├── 如果仍然满足:
        │   ├── YES token 高确定性 → emit "market_resolved"
        │   └── NO token 高确定性 → emit "no_longer_possible"
        └── 如果不满足 → 静默取消
```

**状态转换完整流程图**：

```
                        ┌──────────────┐
                        │  monitoring  │
                        └──────┬───────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
```

### 1.7 BBO 漂移检测与修正

```
_check_bbo_drift(asset_id, change):
    │
    ├── 冷却期: 每个 asset_id 60 秒内只检查一次
    │
    ├── 从 price_change 消息中提取 server 报告的 bestBid/bestAsk
    │
    ├── 与本地 LocalOrderBook 的 BBO 比较
    │
    └── 如果偏差 > 1e-9:
        ├── 记录冷却时间
        ├── 日志警告
        └── 触发 resync_token(asset_id)
            → SharedMarketWebSocket 退订 + 100ms + 重新订阅 (带 initial_dump)
```

**周期性 resync（每 10 分钟）**：

```
_periodic_resync():
    每 600 秒执行一次
    对所有已订阅 token 逐个 resync
    间隔 = 600s / token数量 (错开避免集中请求)
```

### 1.8 日期翻转机制

```
_rollover_loop():
    │
    ├── 计算下一次翻转时间:
    │   min(每个城市的下一个本地午夜转为UTC)
    │   例: 纽约 EDT 00:00 = UTC 04:00
    │       东京 JST 00:00 = UTC 15:00
    │       取最早的那个
    │
    ├── sleep 到该时刻
    │
    └── coordinator.refresh_local_days():
        ├── 重新计算每个城市的本地日期
        ├── 找出日期已变化的城市
        ├── 对变化的城市重新发现市场
        ├── 替换旧监视器，安装新监视器
        ├── 清除旧事件的信号缓存
        └── 刷新信号计数
```

```
            │   → Signal(signal_id, signal_type="sweep", token_id, market_slug, payload)
            │
            └── _dispatch_signal(signal):
                for strategy in pool.all_instances():
                    strategy.on_signal(signal)
```

#### 2.3.1 入场阶段 (enter)

```
enter(signal):
    │
    ├── 1. 计算下单量 (同步，优先完成):
    │       fixed_entry_shares = 配置值 (默认 100)
    │       max_shares = available_cash / 0.99
    │       actual_shares = min(fixed_entry_shares, max_shares)
    │       如果 actual_shares <= 0 → 关闭 (无可用资金)
    │
    ├── 2. 并行执行 (买单优先调度):
    │       ┌── create_task: place_order(BUY @ 0.99)  ← 先调度，先发出
    │       └── create_task: risk.start(orderbook_snapshot)
    │       await gather(order_task, risk_task)
    │
    │       买单和风控启动并行执行，买单的网络请求最先发出，
    │       风控订阅在等待买单响应的同时完成。
    │
    ├── 3. 处理买单结果:
    │       │
    │       ├── 失败 (insufficient_balance 等) → 关闭交易
    │       └── 成功 → 记录 entry_order_id
    │           ├── 已全部成交 → position_shares += filled
    │           └── 部分成交/挂单中 → 等待
    │
    └── 4. 启动入场超时计时器:
            等待 entry_wait_ms (默认 30000ms = 30秒)
            │
            └── 超时后:
                ├── 取消未成交的买单
                ├── position_shares == 0 → 关闭 (无持仓)
                └── position_shares > 0 → state = "exit_working"
```

#### 2.3.2 监控阶段 — tick 变化检测

```
RiskMonitor._on_tick(tick_size):
    │
    └── 如果 tick_size == 0.001:
        │
        └── SweepTrade._on_tick_change(Decimal("0.001")):
            │
            ├── 已经验证过? → 忽略
            ├── 状态不在 entry_working/exit_working? → 忽略
            │
            └── TickVerifier.verify(token_id):
                │ HTTP 调用 CLOB API 获取 tick_size
                │ 持续重试，指数退避 (1s → 2s → 4s → 5s 封顶)
                │ 最长持续 30 分钟
                │
                ├── confirmed=True:
                │   ├── 再次检查状态 (防止等待期间被风控关闭)
                │   │   状态已不在 entry_working/exit_working → 返回
                │   └── _tick_exit()
                │
                └── timeout (30分钟未确认):
                    └── 忽略，交易保持当前状态等待下次触发
```

#### 2.3.3 正常退出 (tick_exit)

```
_tick_exit():
    │
    ├── 如果 position_shares <= 0:
    │   └── 停止风控 → 关闭交易
    │
    ├── state = "exit_working" (风控继续运行!)
    │
    ├── 下卖单: SELL @ 0.999, size = position_shares
    │
    ├── 如果立即全部成交:
    │   └── position_shares = 0 → 停止风控 → 关闭交易 ✓
    │
    └── 如果未全部成交 (卖单挂在 orderbook 上):
        ├── 记录 exit_order_id
        ├── 启动退出超时计时器 (exit_wait_ms, 默认 300000ms = 5分钟)
        │
        │   期间风控持续运行:
        │   - 如果价格跌破止损 → 风控触发 → 取消 0.999 卖单 → 市价清仓
        │
        └── 超时后 (_exit_timeout):
            ├── 取消 exit_order_id 的卖单
            ├── 如果仍有持仓 → 以 0.01 市价强卖
            └── 停止风控 → 关闭交易
```

**关键设计**：卖单挂出后风控不停止。如果 0.999 的卖单长时间未成交而市场开始反转（比如温度预报修正），风控能及时止损，不会让持仓被套。

#### 2.3.4 风控退出 (risk_exit)

```
RiskMonitor._on_bbo(best_bid, best_ask):
    │
    ├── bid = best_bid 如果存在，否则 0
    │   ask = best_ask 如果存在，否则 1
    │   current_mid = (bid + ask) / 2
    │
    └── 如果 current_mid <= reference_mid × stop_loss_ratio:
        │ 例: 入场时 mid=0.60, ratio=0.60, threshold=0.36
        │ 如果当前 mid 跌到 0.36 → 触发
        │
        └── SweepTrade._risk_exit():
            │
            ├── 取消入场超时计时器
            ├── 取消退出超时计时器
            │
            ├── 如果有未成交买单 (entry_order_id):
            │   └── 取消买单
            │
            ├── 如果有未成交卖单 (exit_order_id):
            │   └── 取消卖单 (撤回 0.999 的挂单)
            │
            ├── 如果有持仓:
            │   └── 以 0.01 价格挂卖 (市价清仓)
            │
            └── 关闭交易, reason="stop_loss"
```

**BBO 缺失处理**：当某侧没有报价时，best_bid 缺失视为 0，best_ask 缺失视为 1。这意味着：
- 只有 ask 没有 bid → mid = ask/2 (偏低，更容易触发止损 — 保守)
- 只有 bid 没有 ask → mid = (bid + 1)/2 (偏高，不容易误触发)
- 两者都没有 → mid = 0.5

#### 2.3.5 强制退出 (force_exit)

```
force_exit(reason="config_disabled"):
    │ 触发场景: 配置变更、策略禁用、手动干预
    │
    ├── 取消入场计时器
    ├── 取消退出计时器
    ├── 停止 RiskMonitor
    │
    ├── 如果有未成交买单 (entry_order_id):
    │   └── 取消买单
    │
    ├── 如果有未成交卖单 (exit_order_id):
    │   └── 取消卖单
    │
    ├── 如果有持仓:
    │   └── SELL @ (1 - tick_size)
    │       如果 tick=0.01 → 卖 @ 0.99
    │       如果 tick=0.001 → 卖 @ 0.999
    │
    └── 关闭交易
```

### 2.4 配置变更与实例生命周期管理

#### 2.4.1 InstancePool 热更新机制

```
InstancePool.reload():
    │
    ├── 从 DB 重新加载所有 enabled 配置
    │
    ├── 对比当前运行中的实例:
    │   │
    │   ├── DB 中已不存在 → destroy(reason="config_disabled")
    │   │   即: force_exit 所有活跃交易
    │   │
    │   ├── DB 中新增 → create 新实例
    │   │
    │   └── params_version 变化 → destroy 旧实例 + create 新实例
    │       即: force_exit 所有活跃交易, 然后用新参数重建
    │
    └── 返回 {stopped: [...], started: [...], reloaded: [...]}
```

#### 2.4.2 配置修改时交易的处理

当用户通过 API 修改一个策略配置（如改变 `stop_loss_ratio`、`fixed_entry_shares` 等）：

1. API 更新 DB 中的配置行，`params_version` 自增
2. 调用 `POST /internal/reload` 触发 InstancePool 热更新
3. InstancePool 检测到 `params_version` 变化
4. **对旧实例调用 `destroy("config_changed")`**：
   - 遍历所有活跃的 `SweepTrade`
   - 对每笔交易调用 `force_exit("config_changed")`
   - 取消所有未成交订单（买单 + 卖单）
   - 以当前 tick_size 对应的价格卖出持仓
   - 关闭交易，记录 event_closed reason="force_exit"
5. **创建新实例**：用新参数创建 SweepStrategy
6. 新实例从下一个信号开始，使用新参数运行

```
配置修改时序:

  用户修改配置 → API → DB (params_version++)
       │
       ▼
  POST /internal/reload
       │
       ▼
  InstancePool.reload()
       │
       ├── 发现 version 变化
       │
       ├── destroy 旧实例:
       │   └── SweepStrategy.destroy("config_changed")
       │       └── force_exit 每笔活跃交易:
       │           ├── 取消挂单 (买/卖)
       │           ├── 卖出持仓 @ (1 - tick_size)
       │           └── 记录 event_closed
       │
       └── create 新实例 (新参数)
           └── 等待下一个信号
```

#### 2.4.3 配置禁用/删除时的处理

```
禁用 (enabled=0):
  reload 时发现该 config_id 不再出现在 enabled 列表
  → destroy(reason="config_disabled")
  → force_exit 所有交易
  → 实例从 pool 中移除

软删除 (deleted_at 非空):
  同上，WHERE deleted_at IS NULL 过滤掉该配置
  → destroy + force_exit
```

#### 2.4.4 关键保证

- **不会有孤儿订单**：无论何种原因关闭，都会先取消所有未成交挂单
- **不会有未管理持仓**：有持仓时必先卖出才关闭
- **配置变更不丢失**：旧交易完整收尾后新实例才开始
- **风控全程覆盖**：从买单发出到所有份额卖出，风控持续监控

### 2.6 交易盈利逻辑

```
典型交易 (NO token sweep):

  1. 检测到 "86-87°F" 的 NO token 在 0.99 被 sweep
     此时 NO token mid ≈ 0.60, 意味着市场认为 60% 概率超过 87°F

  2. 策略认为: sweep 说明有知情者大量买入 NO，真实概率更高
     以 0.99 买入 NO token

  3. 等待市场确认: 如果实际温度确实超过 87°F
     NO token tick 缩到 0.001, best_bid 到 0.995+

  4. 以 0.999 卖出 → 盈利 0.009/share (约 0.9%)

  对于 100 shares @ $0.99 = $99 成本
  卖出 100 shares @ $0.999 = $99.9
  净利润 = $0.90 (扣除手续费前)

时间窗口: 通常几分钟到几小时
风险: 如果 sweep 是虚假信号, mid_price 可能跌破止损线
```

```
    │  (60s 后仍高确定性)       │                          │
    │─────────────────────────▶│                          │
    │                          │ _confirm() 触发          │
    │                          │ NO token → "no_longer_possible"
    │                          │ → _promote_next()        │
    │                          │ → 广播事件               │
    │                          │                          │
```

## 第五部分：关键设计决策与权衡

### 5.1 为什么使用单 WebSocket 连接？

Polymarket CLOB Market Channel 是按 token 订阅的。50 个城市 × 2 个方向 × 2 个 monitor × 2 个 token = 最多 400 个 token。单连接批量订阅比 400 个独立连接高效得多，且更容易管理重连。

### 5.2 为什么需要双监视器前瞻？

没有 next_monitor 时，当 main 的 NO token 确认为高确定性后：
1. 需要通过 HTTP 找到下一个 candidate
2. 订阅 WebSocket
3. 等待初始 dump
4. 才能开始检测

这个延迟窗口可能错过连续 sweep。有 next_monitor 后，promote 是瞬时的。

### 5.3 为什么 sweep 只检测概率较高的一侧？

如果一个 token 当前 mid 只有 0.10（低概率），它的 0.99 ask 被清空并不意味着什么 — 可能只是流动性本来就薄。只有当一个 token 已经是"被看好"的一方时，0.99 被 sweep 才是强信号。

### 5.4 为什么 tick 确认需要 HTTP 校验？

WebSocket 可能有延迟、丢消息或误报。在执行高价卖出（0.999）前，必须通过 HTTP REST API 独立确认 tick_size 确实为 0.001，避免因为 tick 还是 0.01 而挂出不可能成交的订单。

### 5.5 为什么高确定性需要 60 秒确认？

tick 缩小到 0.001 后，市场可能短暂出现高确定性状态然后回退（大单被吃、做市商调整等）。60 秒等待过滤掉瞬态波动，只有真正确认的市场才会触发状态推进。

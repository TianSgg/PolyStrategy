# 内存订单簿漂移问题分析与解决方案

## 问题描述

前端展示的订单簿数据（来自后端内存维护的 `LocalOrderBook`）与 Polymarket 网站上真实的订单簿存在差异。

## 技术前提

- WebSocket 基于 TCP，**保证数据按序、完整到达**，不会静默丢包
- 如果网络中断，TCP 连接会断开（不是静默丢数据）
- 因此"网络层丢消息"不是有效原因，问题一定出在应用层

## 数据流路径

```
Polymarket CLOB WS → SharedMarketWebSocket._dispatch()
                          → Monitor.deliver()
                              → LocalOrderBook.apply_snapshot() / apply_change()
                                  → _publish_book_update() → SSE → 前端
```

## 当前订阅机制

系统对每个温度市场：
- **持久订阅 NO token** → 获得 NO 的 initial dump + 整个市场的 `price_change` 事件（含 YES 和 NO 的变动）
- **临时订阅 YES token** → 仅获取 YES 的 initial dump，收到后立即取消订阅

根据 Polymarket 官方文档，`price_change` 事件是市场级别的（一条消息包含该市场所有 token 的变动），所以持久订阅 NO token 就能持续收到 YES token 的增量更新。

---

## 问题原因分析

### 原因 1：缺少应用层心跳（致命级）

**Polymarket 官方文档明确要求：**
> The market WebSocket uses an application-level heartbeat. Send the text frame `PING` every 10 seconds; the server replies with `PONG`.

**当前代码（gateway.py 第 169-170 行）：**
```python
async with websockets.connect(
    MARKET_WS_URL,
    ping_interval=20,    # 这是 WebSocket 协议层 ping，不是应用层
    ping_timeout=20,
)
```

我们只使用了 websockets 库的**协议层 ping/pong**（RFC 6455 控制帧），**没有发送 Polymarket 要求的应用层 "PING" 文本帧**。

**后果**：Polymarket 服务端可能因为收不到应用层心跳而：
- 认为客户端已死，停止推送消息（连接看似正常但无数据流入）
- 主动关闭连接（触发重连，但重连间隙丢数据）
- 降低推送优先级或限流

这是**最可能的漂移根本原因** — 服务器在某个时刻停止推送部分或全部 `price_change` 消息，而我们的连接表面上仍然存活。

### 原因 2：YES token 的 `book` 事件无法接收

`book` 事件（全量快照）是针对**特定 token** 的，只有订阅了该 token 才能收到。

当前情况：
- NO token 持久订阅 → 可以收到 NO 的 `book` 事件
- YES token 在获取 initial dump 后立即取消订阅 → **永远不会再收到 YES 的 `book` 事件**

如果 Polymarket 偶尔发送 `book` 事件作为全量修正（比如在检测到客户端可能不同步时），YES token 的修正我们会错过。YES book 一旦漂移就永远不会被修正，只能等重连。

### 原因 3：重连间隙丢失数据

TCP 连接断开到重新建立期间（通常 1-30 秒），所有变化丢失。重连后通过 initial dump 可以修正，但存在时间窗口：

1. 旧连接断开
2. 新连接建立，发送 subscribe（包含 initial_dump）
3. 在收到 initial dump 之前，可能已经开始收到 `price_change` → 这些变化应用到了旧的 book 上
4. Initial dump 到达，覆盖 book → 正确
5. 但如果 initial dump 和后续 price_change 之间有间隙（服务端在生成 dump 之后、发送之前又有变化），这部分会丢失

此外，`_on_ws_reconnect` 通过 `asyncio.create_task` 异步执行，YES token 的重新订阅可能晚于消息接收循环开始。

### 原因 4：`hash` 字段未被利用

Polymarket 的 `book` 和 `price_change` 事件都包含 `hash` 字段：

```json
// book 事件
{"event_type": "book", "hash": "0xabc123…", "bids": [...], "asks": [...]}

// price_change 事件
{"price_changes": [{"hash": "56621a...", "best_bid": "0.08", "best_ask": "0.09"}]}
```

这个 hash 可以用来**验证本地 book 状态是否与服务端一致**。当前代码完全忽略了这个字段，错失了检测漂移的机会。

### 原因 5：Polymarket 前端可能使用不同数据源

Polymarket 网站本身可能：
- 使用不同的 API 端点或更高优先级的数据推送
- 包含隐藏流动性（iceberg orders）
- 有不同的聚合/展示规则
- 使用更高频率的全量刷新

如果是这个原因，则两边的数据"不一致"可能是数据源差异，而非我们的 bug。

## 解决方案

### 方案 A：实现应用层心跳（最高优先级）

**修复缺少 PING 心跳的问题** — 这是必须立即修复的 bug。

**实现位置**：`SharedMarketWebSocket._run()`

**实现思路**：
```python
async def _run(self) -> None:
    delay = 1
    while True:
        try:
            async with websockets.connect(
                MARKET_WS_URL,
                ping_interval=None,   # 禁用协议层 ping，改用应用层
                ping_timeout=None,
                max_size=2 * 1024 * 1024,
            ) as ws:
                self._ws = ws
                self.connected = True
                # ... 重新订阅逻辑 ...

                # 启动应用层心跳
                heartbeat_task = asyncio.create_task(self._heartbeat(ws))
                try:
                    async for raw in ws:
                        if raw == "PONG":
                            continue  # 心跳回复，忽略
                        self._dispatch(raw)
                finally:
                    heartbeat_task.cancel()
        except ...

async def _heartbeat(self, ws):
    """每 10 秒发送应用层 PING"""
    while True:
        await asyncio.sleep(10)
        await ws.send("PING")
```

**优先级**：P0 — 不修复这个，其他优化都可能无效

---

### 方案 B：定期全量重同步

**原理**：每隔固定间隔，重新发送订阅请求（带 initial_dump=True），强制获取最新全量快照。

**实现思路**：
```python
RESYNC_INTERVAL = 300  # 每 5 分钟

async def _periodic_resync(self):
    while True:
        await asyncio.sleep(RESYNC_INTERVAL)
        async with self._lock:
            if not self._ws or not self.connected:
                continue
            # 错开重同步，避免同时大量数据
            for token_id in list(self._subscribed_tokens):
                await self._ws.send(json.dumps({
                    "assets_ids": [token_id],
                    "type": "market",
                    "operation": "subscribe",
                    "level": 2,
                    "initial_dump": True,
                }))
                await asyncio.sleep(2)  # 错开 2 秒
```

同时需要为 YES token 也周期性获取 initial dump（因为 YES token 已从 wire 取消订阅，无法通过重新订阅获得 book 事件）：
```python
# 同时对所有 YES token 请求临时 initial dump
for state in self._states.values():
    for monitor in (state.main_monitor, state.next_monitor):
        if monitor and monitor.running:
            yes_id = monitor.candidate.yes_asset.asset_id
            await self._shared_ws.subscribe_for_initial_dump(yes_id)
            await asyncio.sleep(1)
```

**优先级**：P1 — 作为兜底机制，即使心跳正常也有可能因为其他原因产生微小漂移

### 方案 C：基于 hash 的一致性检测

**原理**：利用 Polymarket 提供的 `hash` 字段，在每次收到 `price_change` 时验证本地状态是否与服务端一致。如果不一致，立即触发全量重同步。

**实现思路**：
```python
def apply_change(self, price, size, side, best_bid=None, best_ask=None):
    # 应用变更
    levels = self.asks if side == "SELL" else self.bids
    numeric_price, numeric_size = float(price), float(size)
    if numeric_size <= 0:
        levels.pop(numeric_price, None)
    else:
        levels[numeric_price] = numeric_size

    # 用 best_bid/best_ask 做简单一致性校验
    if best_bid is not None:
        local_best_bid = max(self.bids, default=None)
        if local_best_bid is not None and abs(local_best_bid - float(best_bid)) > 1e-9:
            return "DRIFT_DETECTED"  # 触发重同步
    if best_ask is not None:
        local_best_ask = min(self.asks, default=None)
        if local_best_ask is not None and abs(local_best_ask - float(best_ask)) > 1e-9:
            return "DRIFT_DETECTED"
```

注意：`price_change` 中每个条目包含 `best_bid` 和 `best_ask` 字段，这就是服务端认为的当前 BBO。我们可以直接用这个来校验本地 BBO 是否一致。

**优先级**：P1 — 低成本的实时检测机制，能精确知道何时发生了漂移

---

### 方案 D：重连状态隔离

**原理**：重连后，在收到 initial dump 之前丢弃该 asset 的所有增量消息。

**实现思路**：
```python
class WeatherOrderBookMonitor:
    def __init__(self, ...):
        self._awaiting_snapshot: set[str] = set()

    def mark_awaiting_snapshot(self):
        """重连后调用"""
        self._awaiting_snapshot = set(self._assets.keys())

    def deliver(self, data):
        if isinstance(data, list):
            for snapshot in data:
                asset_id = snapshot.get("asset_id")
                if asset_id in self._assets:
                    self._awaiting_snapshot.discard(asset_id)
                    self._books[asset_id].apply_snapshot(...)
            return

        if data.get("event_type") == "price_change":
            # 如果任何相关 asset 还在等 snapshot，跳过整个消息
            for change in data.get("price_changes", []):
                if change.get("asset_id") in self._awaiting_snapshot:
                    return
            # ... 正常处理
```

**优先级**：P2 — 辅助手段，减少重连窗口内的脏数据

## 推荐实施顺序

| 优先级 | 方案 | 解决的问题 | 复杂度 | 效果 |
|--------|------|-----------|--------|------|
| P0 | 方案 A（应用层心跳） | 服务端停止推送 | 极低 | 可能直接解决问题 |
| P1 | 方案 C（BBO 一致性检测） | 精确检测漂移发生时刻 | 低 | 漂移感知能力 |
| P1 | 方案 B（定期重同步） | 任何原因的累积漂移 | 低 | 兜底修复 |
| P2 | 方案 D（重连状态隔离） | 重连期间脏数据 | 中 | 减少重连影响 |

**建议先实现方案 A**，观察漂移是否消失。如果仍有漂移，再逐步加入 B 和 C。

---

## 验证方法

修复后可以通过以下方式验证效果：

1. **对比测试**：定时通过 HTTP API `GET /book?token_id=xxx` 拉取 Polymarket 的真实订单簿，与内存中的 book 对比 BBO
2. **日志监控**：在检测到漂移时记录日志，统计漂移频率和幅度
3. **前端展示**：在前端 orderbook 旁边显示"最后同步时间"和"BBO 校验状态"

# 策略执行系统实施计划

状态：待评审

## 1. 实施原则

1. 先抽取共享能力，再上线策略 1；不在已有 `CopyTradingService` 中继续叠加策略分支。
2. 首期即为“五个独立进程、同机部署”：两个信号服务分别提供 loopback WebSocket Server，三个策略服务分别作为 WebSocket Client 订阅。新策略链路不得使用进程内 `EventBus`、Redis 或持久化消息流。
3. 订单、资金和运行状态必须先以可测试的领域模型实现，再接入真实 CLOB 客户端。
4. 新表、新 API、新页面与当前跟单表/API 并存；迁移完成且完成数据核对前，不修改或删除原有跟单路径。
5. 每个阶段可独立上线、回滚并对应一个或少数几个 Git 提交。

## 2. 目标代码边界与完整目录

不新建一个泛化的顶级 `services/` 目录，也不移动现有业务模块。新增的策略系统全部放入 `backend/src/strategy_execution/`；这样保留当前 `account`、`weather_orderbook`、`copy_trading` 等稳定的模块边界，并避免策略代码再次集中到 `copy_trading.service`。

关键边界：天气订单簿服务与 Leader Activity 服务各自拥有信号接收、规范化、去重、WebSocket 广播及异步数据保存，绝不下单；`signal_data/` 只是两者共用的数据契约和分析代码，不是第六个微服务；`strategy_execution/` 只能通过 `signal_subscription.py` 订阅两个 WS 服务，绝不拥有原始信号表或来源 adapter；`strategies/` 只能做策略状态迁移和调用执行内核，不能直接访问 CLOB client 或写 SQL；`execution/` 是唯一能发单、撤单和修改内存资金账本的地方。

现有模块的接入方式：

| 现有模块 | 改造后的角色 | 首期变更 |
| --- | --- | --- |
| `weather_orderbook` | 微服务 1：天气订单簿信号源 | 不复制订单簿；`signal_ws.py` 通过 loopback WS 广播 sweep，并异步保存统一信号和盘口上下文。 |
| `copy_trading.predexon` | Leader activity 的现有接入点 | 将接收能力提取至独立 `leader_activity` 微服务（微服务 2），通过 loopback WS 广播含 outcome 的 activity，并异步保存数据。 |
| `market.service` | 普通市场共享订单簿与 tick 元数据 | 提供只读 BBO/tick 订阅适配；新风险模块复用，避免重复建 WS。 |
| `copy_trading.ws` | follower user-channel 订单/成交回报来源 | 先增加向执行器分发回报的适配层，后续再考虑独立 user WS。 |
| `account.service` | 账户凭据和账户归属 | 提供预热客户端所需凭据，严禁向前端泄露。 |

## 3. 信号服务与策略执行数据库表设计

迁移拆分为 `backend/migrations/V7__create_signal_data_schema.sql` 与 `V8__create_strategy_execution_schema.sql`。前者先独立上线，验证两个信号服务的数据保存和分析；后者才创建真正交易所需的配置、运行和订单表。新表不修改、不复用 `copy_trading_orders`：两套运行模型并存，便于灰度和回滚。当前项目既有表没有外键，本迁移也不加数据库外键，而由 API/Repository 做归属校验；这样避免历史数据、账户删除和长时间订单回放被外键阻断。逻辑关系和索引必须完整保留。

```text
signal_events 1 ── N signal_market_contexts
       │
       ├── 1 ── N signal_analysis_features
       └── N ── N strategy_runs（经 strategy_run_signals）

strategy_configs 1 ── N strategy_config_signal_bindings
       │
       └── 1 ── N strategy_runs 1 ── N strategy_run_events
                                    ├── N strategy_run_signals N ── 1 signal_events
                                    ├── N strategy_orders
                                    ├── N strategy_account_ledger
                                    └── N strategy_run_snapshots
```

### 3.1 表、字段与约束

#### `strategy_configs`：用户可配置的策略实例

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 主键、自增。 |
| `owner_user_id` | `INT` | 非空；与 `accounts.owner_user_id` 一致性由应用校验。 |
| `account_id` | `INT` | 非空；执行账户。 |
| `name` | `VARCHAR(128)` | 非空；同一用户内展示名唯一。 |
| `strategy_type` | `VARCHAR(32)` | 非空：`sweep`、`leader`、`combined`。用字符串而非 MySQL ENUM，利于新增策略。 |
| `enabled` | `TINYINT(1)` | 默认 `0`；启用才预热 client/接收信号。 |
| `params_json` | `JSON` | 非空；已校验的策略参数快照。 |
| `params_version` | `SMALLINT UNSIGNED` | 默认 `1`；配置 schema 演进。 |
| `created_at/updated_at` | `DATETIME(3)` | UTC+8，遵循现有项目时间约定。 |

索引：`UNIQUE(owner_user_id, name)`、`INDEX(account_id, enabled)`、`INDEX(owner_user_id, enabled, strategy_type)`。

#### `strategy_config_signal_bindings`：配置的信号订阅条件

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 主键、自增。 |
| `strategy_config_id` | `BIGINT UNSIGNED` | 非空；逻辑关联配置。 |
| `source_type` | `VARCHAR(32)` | `weather` 或 `leader`。 |
| `leader_proxy_wallet` | `VARCHAR(128)` | leader/combined 使用，小写存储；天气绑定为 `NULL`。 |
| `event_type` | `VARCHAR(64)` | 如 `sweep`、`leader_buy`。 |
| `outcome_filter` | `VARCHAR(8)` | `yes`、`no`、`all`。 |
| `enabled` | `TINYINT(1)` | 默认 `1`。 |
| `created_at/updated_at` | `DATETIME(3)` | 审计时间。 |

索引：`UNIQUE(strategy_config_id, source_type, event_type, leader_proxy_wallet)`、`INDEX(source_type, event_type, leader_proxy_wallet, enabled)`。此表使运行期能以来源和 leader 快速定位配置，避免每个信号遍历全部策略。

#### `signal_events`：两个信号服务共同写入的规范化业务信号

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `CHAR(36)` | 主键 UUID，由产生该事件的信号服务生成。 |
| `source_type` | `VARCHAR(32)` | `weather` / `leader`。 |
| `source_event_id` | `VARCHAR(256)` | 上游的稳定幂等键。 |
| `event_type` | `VARCHAR(64)` | `sweep` / `leader_buy` 等。 |
| `token_id` | `VARCHAR(128)` | 非空。 |
| `outcome/side` | `VARCHAR(8)` | 可空；`yes/no`、`BUY/SELL`。 |
| `leader_proxy_wallet` | `VARCHAR(128)` | leader 信号可用。 |
| `occurred_at` | `DATETIME(3)` | 上游事件发生时间。 |
| `received_at` | `DATETIME(3)` | 本服务收到时间。 |
| `received_monotonic_ns` | `BIGINT UNSIGNED` | 仅延迟审计；重启后不可比较。 |
| `payload_json` | `JSON` | 原始来源 payload 与规范化补充字段，用于审计和回放。 |

索引：`UNIQUE(source_type, source_event_id)`、`INDEX(token_id, received_at)`、`INDEX(leader_proxy_wallet, received_at)`、`INDEX(event_type, occurred_at)`。关键路径先走各信号服务自己的内存 TTL 去重；该表用于异步写入后的检索、离线分析和审计兜底。它属于 `signal_data.repository`，策略模块只有只读关联权限。

#### `signal_market_contexts`：信号触发时的盘口上下文

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 主键、自增。 |
| `signal_id` | `CHAR(36)` | 非空，关联 `signal_events.id`。 |
| `token_id` | `VARCHAR(128)` | 非空，方便按 token 分析。 |
| `observed_at` | `DATETIME(3)` | 非空，盘口观测时间。 |
| `tick_size` | `DECIMAL(18,8)` | 可空。 |
| `best_bid/best_ask` | `DECIMAL(36,18)` | 可空。 |
| `bid_depth/ask_depth` | `DECIMAL(36,18)` | 可空，定义为策略可用价格区间的累计份额。 |
| `bid_levels/ask_levels` | `INT UNSIGNED` | 可空。 |
| `book_summary_json` | `JSON` | 可空，保存有限深度、sweep 前后对比等。 |

索引：`INDEX(signal_id, observed_at)`、`INDEX(token_id, observed_at)`。此表只记录业务信号前后指定窗口的快照/抽样；不把每一条 CLOB 高速更新写入 MySQL。

#### `signal_analysis_features`：可版本化的研究特征

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 主键、自增。 |
| `signal_id` | `CHAR(36)` | 非空。 |
| `feature_set` | `VARCHAR(64)` | 如 `weather_sweep_v1`、`leader_trade_v1`。 |
| `feature_version` | `SMALLINT UNSIGNED` | 非空。 |
| `computed_at` | `DATETIME(3)` | 非空。 |
| `features_json` | `JSON` | 非空；例如 sweep 深度、价格冲击、leader 历史统计。 |

索引：`UNIQUE(signal_id, feature_set, feature_version)`、`INDEX(feature_set, computed_at)`。分析任务可重算新版本特征而不覆盖旧数据，便于研究结果可复现。

#### `strategy_runs`：一个 token 的完整策略运行聚合

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `CHAR(36)` | 主键 UUID；日志、前端、订单共同使用。 |
| `strategy_config_id` | `BIGINT UNSIGNED` | 非空。 |
| `token_id` | `VARCHAR(128)` | 非空。 |
| `market_slug/question/outcome` | `VARCHAR(255/512/8)` | 创建时写入展示快照，后续不依赖外部 API 回查。 |
| `state` | `VARCHAR(32)` | 非空：如 `ENTRY_WORKING`、`WAITING_LEADER`、`EXIT_WORKING`、`CLOSED`。 |
| `status` | `VARCHAR(16)` | 非空：`ACTIVE`、`CLOSED`、`FAILED`、`RECOVERY_REQUIRED`。 |
| `active_key` | `VARCHAR(256)` | 活跃时为 `{config_id}:{token_id}`，关闭时置 `NULL`。 |
| `params_snapshot_json` | `JSON` | 创建时冻结参数，运行中改配置不得影响已有单子。 |
| `started_by_signal_id` | `CHAR(36)` | 初始 `signal_events.id`。 |
| `avg_entry_price` | `DECIMAL(36,18)` | 无成交时可空。 |
| `entry_shares/exited_shares` | `DECIMAL(36,18)` | 默认 0，按已确认成交更新。 |
| `risk_state` | `VARCHAR(32)` | `OFF/ACTIVE/TRIGGERED/FORCE_STOPPED`。 |
| `close_reason` | `VARCHAR(64)` | 正常关闭、tick exit、risk exit、超时等。 |
| `version` | `INT UNSIGNED` | 默认 1，更新时乐观锁。 |
| `started_at/ended_at/created_at/updated_at` | `DATETIME(3)` | 生命周期及审计时间。 |

索引：`UNIQUE(active_key)`（MySQL 允许多个 `NULL`，实现每配置每 token 只有一个活跃 run）、`INDEX(strategy_config_id, status, started_at)`、`INDEX(token_id, status, started_at)`、`INDEX(started_by_signal_id)`。

#### `strategy_run_signals`：运行与多个信号的关联

组合策略一个 run 会关联 sweep 和 leader 两个信号，不能只在 `strategy_runs` 保存一个信号字段。

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `run_id` | `CHAR(36)` | 非空。 |
| `signal_id` | `CHAR(36)` | 非空。 |
| `role` | `VARCHAR(32)` | `entry_sweep`、`leader_confirm`、`ignored` 等。 |
| `linked_at` | `DATETIME(3)` | 非空。 |

主键/索引：`PRIMARY KEY(run_id, signal_id)`、`INDEX(signal_id)`。

#### `strategy_run_events`：不可变运行时间线

| 字段 | 类型 | 约束/说明 |

### 3.2 迁移与保留策略

- V7 只上线两个信号服务的数据保存：先验证天气和 Leader 信号可被完整保存、查询、离线分析和计算特征，且不向任何策略投递真实下单请求。
- 所有新配置默认 `enabled=0`，V8 迁移本身不会创建/启用任何真实策略。
- 旧 `copy_trading_configs`、`copy_trading_orders` 和现有天气通知表不做数据迁移；旧功能继续工作。
- 策略配置删除采用软删除/停用：已有 `strategy_runs` 永远保留；`strategy_configs` 不做物理删除，新增 `deleted_at`（可空）字段即可。
- 运行状态、订单状态和账本均追加而非覆盖；可变的当前快照只存在于 `strategy_runs`/`strategy_orders`，历史以事件表为准。
- V7 后的后续字段变动必须使用 V8+ 迁移，禁止直接修改 V7 或在应用启动时 `ALTER TABLE`。

## 6. 风险、取舍与未决问题

| 项目 | 决策/风险 | 处理方式 |
| --- | --- | --- |
| “微服务”与 10ms | loopback WebSocket 仍有序列化、调度和 GC 抖动。 | 使用常驻连接、极小消息、非阻塞广播；以实际 P99 测量为准，不把 10ms 当作未经压测的保证。 |
| 数据库阻塞 | 同步写审计会拖慢入场。 | 请求发出后异步落库；内存 ring buffer + 重试，失败告警。 |
| 余额真实性 | REST 轮询有延迟，单纯缓存会超买。 | 实时余额基线 + 原子保留 + user WS/开放单校准。 |
| tick 假阳性 | WS 的 tick 更新可能陈旧或不完整。 | SELL 前 HTTP 强校验并重试；失败时持续风控。 |
| 状态竞态 | cancel、fill、风险、leader 确认可并发。 | run 单飞锁、版本号、不可变事件与幂等订单投影。 |
| 手续费与最小订单 | 可买最大份额若不留余量可能请求失败。 | 账本保留费率缓冲、价格/份额量化和 CLOB 规则校验。 |

上线前需要产品确认的细节：

1. 风控触发后所用的强制退出定价、重试次数和最终人工接管规则；
2. 策略 3 未获 leader 确认但已有部分成交时，默认退场模式选择；
3. `max_available` 是否允许吃尽安全垫之外的全部资金，以及是否按配置间再设置资金配额；
4. leader 信号中 `outcome` 缺失时是丢弃、补查还是按 `all` 处理；建议默认丢弃并记录原因。

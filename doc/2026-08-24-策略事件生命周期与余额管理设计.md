# 策略事件生命周期与余额管理设计

## 1. 概述

本文档描述策略执行系统中：
- 策略配置的创建与启用流程
- Event（交易事件）的完整生命周期
- Phase（阶段）分类与 Step（步骤）对应关系
- 余额管理方案（后台轮询缓存）
- 配置变更/停止时的强制退出处理

---

## 2. 策略配置流程

### 2.1 整体流程

```
添加钱包 → 创建策略配置（选择策略+钱包+参数）→ 启用配置 → 余额轮询开始 → 策略运行
```

### 2.2 步骤详解

#### Step 1：添加钱包（主服务）

用户在主服务中添加 Polymarket 钱包账户：

```
POST /api/accounts
{
  "private_key": "0x...",
  "signature_type": 0
}
```

系统自动完成：
- 从私钥解析 EOA 地址
- 通过 Gamma API 获取 proxy_wallet 地址
- 派生 Builder API 凭据（api_key / secret / passphrase）
- 加密存储到 `accounts` 表

此时钱包已可用，但尚未关联任何策略。

#### Step 2：创建策略配置（主服务）

用户选择策略类型 + 钱包 + 填写参数：

```
POST /api/strategy/configs
{
  "strategy_type": "weather_sweep",
  "proxy_wallet": "0xabc...",
  "name": "天气扫单-主账户",
  "params": {
    "fixed_entry_shares": "100",
    "stop_loss_ratio": "0.60",
    "entry_wait_ms": 30000
  },
  "enabled": false          ← 创建时默认不启用
}
```

写入 `weather_sweep_configs` 表，此时策略不运行。

#### Step 3：启用配置

用户在前端点击"启用"按钮：

```
PUT /api/strategy/configs/:id
{ "enabled": true }
```

后端处理：
1. 更新 DB `enabled = true`
2. 通知策略进程 `POST /internal/reload`
3. 策略进程的 StrategyContainer 执行 reload：
   - 从 DB 加载所有 enabled 的配置
   - 检测到新增配置 → `_start_instance(cfg)`
   - 创建 OrderExecutor
   - **启动 BalancePoller（开始 1s 轮询余额）**
   - 创建 EventLogger
   - 调用 `strategy.start(ctx)`
4. 策略实例开始监听信号

#### Step 4：策略运行中

```
                    BalancePoller (1s 轮询)
                         │
信号源 WS ──→ Container ─┼─→ Instance 1 (config_id=5)
                         │     └── on_signal() → 读缓存余额 → 下单
                         │
                         └─→ Instance 2 (config_id=7)
                               └── on_signal() → 读缓存余额 → 下单
```

### 2.3 前端操作与系统响应对照

| 前端操作 | API 调用 | 系统响应 |
|----------|----------|----------|
| 添加钱包 | POST /api/accounts | 存储账户凭据，缓存 ClobClient |
| 创建配置 | POST /api/strategy/configs | 写入 DB，策略不运行 |
| 启用配置 | PUT /configs/:id {enabled:true} | 启动实例 + BalancePoller |
| 禁用配置 | PUT /configs/:id {enabled:false} | 强制退出 → 停止实例 |
| 修改参数 | PUT /configs/:id {params:...} | 强制退出旧实例 → 启动新实例 |
| 删除配置 | DELETE /configs/:id | 强制退出 → 停止 → 软删除 |

### 2.4 BalancePoller 启动时机

```
配置 enabled=false    → 无 poller，不消耗 API 配额
配置 enabled=true     → poller 启动，每秒轮询余额和挂单
配置 disabled/删除    → 强制退出后 poller 停止（若无其他实例使用同一钱包）
多个配置用同一钱包   → 共享同一个 poller（全局单例 per proxy_wallet）
```

## 3. Event 生命周期

一个 Event 代表一次完整的交易事件：从收到信号到最终平仓。

```
信号到达 → 开仓(entry) → 持仓监控(monitor) → 平仓退出(exit)
```

### 2.1 Phase 定义

| phase | 含义 | 触发条件 |
|-------|------|----------|
| `entry` | 开仓阶段 | 收到合格信号，下买单 |
| `monitor` | 持仓监控阶段 | 买单成交后，监控行情和风控 |
| `exit` | 自然退出 | tick 条件达成，正常卖出 |
| `exit_risk` | 风控退出 | 止损条件触发，紧急卖出 |
| `exit_force` | 强制退出 | 用户禁用/修改配置，强制平仓 |

### 2.2 每个 Phase 对应的 Steps

#### Phase: `entry`（开仓）

| step | 说明 | detail 字段 |
|------|------|-------------|
| `signal_received` | 收到合格的 sweep 信号 | signal_id, token_id, market_slug, event_slug, city, direction |
| `buy_placed` | 买单已提交 | order_id, price, size |
| `buy_filled` | 买单成交（全部或部分） | order_id, filled_size, total_position, fill_price |
| `buy_failed` | 买单失败 | reason (no_cash / insufficient_balance / api_error), requested_size |
| `entry_timeout` | 等待成交超时，撤销买单 | wait_ms, order_id, final_position |

#### Phase: `monitor`（持仓监控）

| step | 说明 | detail 字段 |
|------|------|-------------|
| `risk_started` | 风控监控启动 | entry_price, stop_loss_ratio |
| `tick_detected` | 检测到 tick size 变化 | tick_size, source |
| `tick_verified` | tick 条件已验证确认 | token_id, confirmed |

#### Phase: `exit`（自然退出）

| step | 说明 | detail 字段 |
|------|------|-------------|
| `sell_placed` | 卖单已提交 | order_id, price, size, reason (tick_exit) |
| `sell_filled` | 卖单成交 | order_id, filled_size, fill_price, remaining_position |
| `event_closed` | 事件关闭 | reason (tick_exit / timeout_no_fill), total_position, duration_ms |

#### Phase: `exit_risk`（风控退出）

| step | 说明 | detail 字段 |
|------|------|-------------|
| `stop_loss_triggered` | 止损条件触发 | entry_price, threshold, sell_price, sell_size |
| `sell_placed` | 止损卖单已提交 | order_id, price, size |
| `sell_filled` | 止损卖单成交 | order_id, filled_size, fill_price |
| `event_closed` | 事件关闭 | reason (stop_loss), total_position, duration_ms |

#### Phase: `exit_force`（强制退出）

| step | 说明 | detail 字段 |
|------|------|-------------|
| `force_exit` | 触发强制退出 | reason (config_disabled / config_changed), trigger (user) |
| `buy_cancelled` | 撤销未成交买单 | order_id, cancelled_size |
| `force_sell_placed` | 平仓卖单已提交 | order_id, price, size, tick_size |
| `force_sell_filled` | 平仓卖单成交 | order_id, filled_size, fill_price |
| `event_closed` | 事件关闭 | reason (force_exit), total_position, duration_ms |

## 3. 数据库 Schema

### 3.1 weather_sweep_events 表

```sql
CREATE TABLE weather_sweep_events (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    event_id        VARCHAR(64) NOT NULL,
    config_id       INT NOT NULL,
    owner_user_id   INT,
    proxy_wallet    VARCHAR(64),
    signal_id       VARCHAR(128),
    token_id        VARCHAR(128),
    market_slug     VARCHAR(256),
    event_slug      VARCHAR(256),
    phase           ENUM('entry', 'monitor', 'exit', 'exit_risk', 'exit_force') NOT NULL,
    step            VARCHAR(64) NOT NULL,
    detail          JSON,
    config_snapshot JSON,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_event_id (event_id),
    INDEX idx_config_id (config_id),
    INDEX idx_phase (phase),
    INDEX idx_created_at (created_at)
);
```

### 3.2 查询示例

```sql
-- 查看某个 event 的完整时间线
SELECT phase, step, detail, created_at
FROM weather_sweep_events
WHERE event_id = ?
ORDER BY id;

-- 查看所有被强制退出的事件
SELECT DISTINCT event_id, created_at
FROM weather_sweep_events
WHERE phase = 'exit_force' AND step = 'force_exit';

-- 统计各退出类型占比
SELECT 
  JSON_EXTRACT(detail, '$.reason') as exit_reason,
  COUNT(DISTINCT event_id) as count
FROM weather_sweep_events
WHERE step = 'event_closed'
GROUP BY exit_reason;
```

## 4. 强制退出处理流程

### 4.1 触发条件

- 用户在前端**禁用**配置
- 用户在前端**修改**配置参数

两种情况都会调用策略的 `force_exit()` 方法。

### 4.2 强制退出逻辑

```
force_exit() 被调用
│
├── 当前 state == "idle" 或 "closed"
│   └── 直接停止，无需操作
│
├── 当前 state == "entry_working"（有挂买单）
│   ├── 1. 撤销所有买单
│   ├── 2. 检查是否有已成交份额
│   │   ├── 有份额 → 按 tick_size 最大价格挂卖单
│   │   └── 无份额 → 直接关闭
│   └── 3. 记录 event_closed
│
├── 当前 state == "exit_working"（持仓等待卖出）
│   ├── 1. 按 tick_size 最大价格挂卖单
│   └── 2. 记录 event_closed
│
└── 当前 state == "risk_exiting"（正在止损中）
    └── 不打断，让止损逻辑自行完成
```

### 4.3 卖出价格规则

根据当前 token 的 tick size 决定最大卖价：

| tick_size | 最大卖价 | 说明 |
|-----------|----------|------|
| 0.01 | 0.99 | 标准精度 |
| 0.001 | 0.999 | 高精度（已触发 tick change） |
| 0.0001 | 0.9999 | 超高精度（少见） |

公式：`max_sell_price = 1 - tick_size`

### 4.4 时序图

```
用户禁用配置
    │
    ▼
前端 PUT /api/strategy/configs/:id {enabled: false}
    │
    ▼
后端 _notify_reload() → POST 策略服务 /internal/reload
    │
    ▼
StrategyContainer.reload()
    ├── 检测到 config 被禁用
    ├── 调用 instance.strategy.force_exit("config_disabled")
    │       ├── 记录 step: force_exit
    │       ├── cancel buy orders → 记录 step: buy_cancelled
    │       ├── place sell @ max_price → 记录 step: force_sell_placed
    │       ├── (卖单成交) → 记录 step: force_sell_filled
    │       └── end_event → 记录 step: event_closed
    └── await strategy.stop()
```

## 5. 余额管理设计

### 5.1 问题背景

- 同一个钱包账户可能被多个策略实例使用
- 账户所有者也可能手动操作
- 挂单（pending limit orders）会占用真实余额
- 不能每次下单前实时查 API（延迟太高）

### 5.2 方案：后台轮询缓存（BalancePoller）

```
┌─────────────────────────────────────────┐
│ BalancePoller (per proxy_wallet)        │
│                                         │
│  每 1 秒轮询:                            │
│    ├── get_balance_allowance(COLLATERAL) │
│    └── get_open_orders()                │
│                                         │
│  计算:                                   │
│    available = balance                  │
│              - sum(buy挂单锁定)           │
│              - safety_buffer(2 USDC)    │
│                                         │
│  策略读取: instant (0ms)                 │
│  下单失败: 立即 refresh()                 │
└─────────────────────────────────────────┘
```

### 5.3 挂单锁定计算

```python
locked_usdc = 0
for order in open_orders:
    if order.side == "BUY":
        remaining = original_size - size_matched
        locked_usdc += price * remaining

available_cash = collateral_balance - locked_usdc - safety_buffer
```

所有在 CLOB 上 resting 的 BUY 单都被计入，无论来源（本策略 / 其他策略 / 手动操作）。

### 5.4 轮询频率与限速

| API 接口 | 用途 | 轮询频率 | Polymarket 限速 |
|----------|------|----------|----------------|
| `GET /balance-allowance` | USDC 余额 | 1 次/秒 | 200 次/10秒 |
| `GET /data/orders` | 挂单列表 | 1 次/秒 | 900 次/10秒 |
| `GET /positions` (Data API) | 持仓 | 1 次/5秒 | 150 次/10秒 |

即使 5 个策略进程同时轮询同一账户，总频率也远低于限速。

### 5.5 架构位置

```
策略进程 (strategy_weather_sweep)
├── StrategyContainer
│   ├── Instance 1 (config_id=5, wallet=0xabc)
│   │   └── OrderExecutor → 读缓存
│   └── Instance 2 (config_id=7, wallet=0xabc)
│       └── OrderExecutor → 读缓存（同一 poller）
└── BalancePoller("0xabc")  ←── 1s 轮询，全局单例
```

同一进程内、同一 proxy_wallet 的多个策略实例共享同一个 BalancePoller。

### 5.6 下单流程

```
策略决定下单
    │
    ▼
OrderExecutor.place_order(BUY, price, size)
    │
    ├── 1. 读缓存 available_cash（instant）
    ├── 2. available_cash < notional?
    │       └── YES → 直接返回 insufficient_balance（不发请求）
    ├── 3. 发送请求到 CLOB
    ├── 4. 成功 → 返回结果
    └── 5. 失败 → 触发 refresh() 刷新缓存 → 返回 failed
```

## 6. 配置变更完整流程

### 6.1 启用配置

```
前端启用 → reload → _start_instance(cfg)
                         ├── 创建 OrderExecutor
                         ├── 启动 BalancePoller（立即开始缓存余额）
                         ├── 创建 EventLogger
                         └── strategy.start(ctx)
```

### 6.2 禁用配置（有进行中 event）

```
前端禁用 → reload → force_exit("config_disabled")
                         ├── 撤买单 + 挂卖单
                         ├── 等待卖单成交（短暂）
                         ├── event_closed
                         └── strategy.stop()
```

### 6.3 修改配置（有进行中 event）

```
前端修改参数 → reload → 检测 params_version 变化
                         ├── 旧实例: force_exit("config_changed")
                         │     ├── 撤买单 + 挂卖单
                         │     ├── event_closed
                         │     └── stop()
                         └── 新实例: _start_instance(new_cfg)
                               └── 用新配置开始运行
```

## 7. 前端展示建议

### 7.1 Event 详情时间线

按 phase 分组展示，每个 phase 用不同颜色：

- `entry` → 蓝色（开仓）
- `monitor` → 灰色（监控）
- `exit` → 绿色（正常退出）
- `exit_risk` → 橙色（风控退出）
- `exit_force` → 红色（强制退出）

### 7.2 Event 列表状态标签

从最后一个 step 的 phase 和 reason 推断：

| 条件 | 显示 |
|------|------|
| event_closed.reason == "tick_exit" | 正常退出 |
| event_closed.reason == "stop_loss" | 止损退出 |
| event_closed.reason == "force_exit" | 强制退出 |
| event_closed.reason == "timeout_no_fill" | 超时未成交 |
| event_closed.reason == "buy_failed" | 开仓失败 |
